零点首发 HTTP 领取引擎：把「首个有效请求」提前到 00:00:00.x

  • 日期：2026-10-25
  • 分类：decisions / runbooks
  • 对象：券友站（pdd-clone，纯 HTTP 业务链路）

背景

限量券在零点极短窗口内抢光，决定成败的不是「重试多少次」，而是第一个有效请求有多快发出。 旧实现的问题：

  1. 调度整分对齐漂移，派发本身就迟到（曾 offset_ms=60003）。
  2. 零点才开始建线程、建连接，DNS+TCP+TLS 全在首发路径上。
  3. 零点后先去查资格/取 task_id，把最贵的时间花在非领取请求上。
  4. 文案各写一份，通知里会漏出英文状态码（busy）。

结论（最终形态）

阶段划分

时间 做什么 明确不做
23:45 纯 HTTP 查进度 → 分类 → 打卡 → 复查；只把满 5 天的放进队列；task_id 写快照 —
23:57 派发 run_nightly()：筛选参与账号、预留次数（credit_ledger reserved）、建好工作线程、置内存态 prepared 不写 accounts 表
零点前 10s prepare_claim()：本地完整性检查（UID / PDDAccessToken / task_id）+ conn.connect() 只握手 + 预构造 body/headers 不发任何业务请求（不查资格、不用领取接口预热）
00:00:00 单调时钟门控 + go 放行，同一线程复用预热 socket 发领取 不查资格、不写库、不发通知
00:00 后 串行落库、账本结算、通知 已超时的请求不重发

为什么握手要卡在「零点前 10 秒」而不是派发时

23:57 握手 → 连接闲置约 3 分钟 → 被服务端 keep-alive 回收 → 零点首发反而走「重建连接」，白预热。 所以线程 23:57 就建好（省掉零点创建线程的开销），握手等到 fire_at - 10s。

门控三重保险（缺一不可）

1) 睡到目标前 50ms（剩余 >50ms 才 sleep，避免忙等烧 CPU）
2) 最后 2ms 忙等，压掉调度抖动
3) go.wait() 之后再用单调时钟兜一道：即使 go 被提前 set，也绝不提前发出

mono_target = time.monotonic() + (fire_at - time.time())：用墙上时钟对齐、单调时钟等待， 避免零点前后 NTP 跳变导致提前或错过。提前到达可能被平台直接拒绝，所以「晚 1ms」永远优于「早 1ms」。

重试分类

状态 动作
busy (6071002) 15s 窗口内重试、间隔 200ms、连续 8 次相同即停；状态保持 busy，绝不改写成「券已领完」
auth / rate_limit / verification / sold_out 立即停
收到 success:true 归 pending，复查且 hasReceived=true 才升 received

conn.request() 抛异常 请求未发出 → 重建连接重发一次（安全）

并发

默认 64、上限 256、下限 1，前端可调；零点窗口内同时首发。 ★ 存量数据库值会覆盖代码默认，改默认必须同步迁移 meta 表，否则界面上还是旧值。

验证方式（可复现）

  1. 连接复用必须实测：起本地 HTTPS 服务器，在 TCP accept 层计数。 注意不能在 handler setup() 里数——那只统计「处理过请求的连接」， 预热 socket 被丢弃后 claim 再新建一条也会显示 1，属于假阳性。
  2. 门控精度实测：目标设为 now+2.5s，服务器记录请求到达时刻，比较偏差。
  3. 文案一致性：解析代码里所有可能产出的状态码，逐个断言后端状态表与前端标签表都存在且含中文。
  4. 单元测试覆盖：门控等待、超时 pending 不重发、busy 限窗重试、售罄即停、状态内存态清空、早间窗口。

实际结果

  • 同线程 prepare→claim：TCP accept = 1，prepare 阶段 HTTP 请求数 = 0，握手 7ms 不在首发路径上
  • 跨线程 prepare(A)→claim(B)：accept = 2 → 证明线程本地连接池不可跨线程复用， 所以准备函数必须在发放请求的那个线程里调用
  • 门控到达偏差：+1.5ms（从不提前），单次请求，attempts=1
  • 顺带修掉两个真实缺陷：
  • 早间打卡窗口越界：服务在 08:30 后启动时，第一次调用随机出目标分钟就立刻执行 → 10 点、下午也会打卡； 已修为「仅在 08:00+minute ~ 08:30 内执行」，越窗记跳过日期。
  • offset_ms 基准错误：原先以「今天零点」为基准，兜底/手动重跑时算出十几小时的假值（实测 44146666ms）； 已改为以目标时刻 fire_at 为基准。

教训

  • 「用了连接池」≠「首发连接已预热」；「同进程」≠「同线程」。只有实测量化才能证明省掉了 DNS/TCP/TLS。
  • 文案一致性是功能问题：状态表缺一个键，通知里就会给用户看英文码。
  • 调度器里任何整分 sleep 都会漂移；用「秒级对齐 + 单调时钟 + 目标时刻兜底」三件套。
