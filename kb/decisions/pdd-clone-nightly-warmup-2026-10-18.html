侧栏时间线：23:30 提前检查 / 23:57 准备 / 00:00 尝试领取。

改造前的问题

  1. 调度 while True: ... time.sleep(20)，hm == 0 只在分钟窗口成立 → 实际触发落在 00:00:00–00:00:19 之间，最坏晚 19 秒。

  3. 没有 23:57 准备环节；没有 23:55–00:20 手动核验避让。

单账号最坏要 00:00:24 才点到按钮，多账号串行更久。

改造内容

pdd.py（5 处）

  • 新增 _WARM 预热池 + warm_prepare / warm_drop / warm_drop_all / warm_info。 预热只建 context + 注入 Cookie，不发页面请求，请求数不变。
  • 新增 _wait_state(pg, timeout_ms=9000)：轮询 window.rawData，就绪即返回， 替代固定 2.5 秒硬等。
  • claim(account, ck_info, warm=False)：warm=True 时复用预热 context； 结束时 pg.close() + ctx.close()，用完即回收。
  • MockProvider.claim 同步签名。

server.py（4 处）

  • scheduler() 改为按整分对齐：time.sleep(max(0.25, 60 - time.time() % 60))， 保证 23:57:00 / 00:00:00 准点命中（误差 < 50ms）。
  • 新增 prepare_nightly()：23:57 只对 hosting_state='active' 且 snapshot.status == 'ready' 的账号预热（不可领的账号预热了也没用）。
  • run_nightly 调 claim(..., warm=True)；领取结束 warm_drop_all()； 00:20 再清一次，防上下文泄漏。
  • 新增 rush_window()：23:55–00:20 内 /api/accounts/<id>/refresh 返回 429「抢券时段，手动核验已暂停」，避免手动核验抢占浏览器线程。

隐患修复：reserved 额度僵死自愈

问题：run_nightly 在 claim() 前插一条 credit_ledger.state='reserved' 占用 1 次额度。 成功转 spent、失败转 released，但进程若在 claim 途中被杀，这条永远停在 reserved。 user_credits() 把 reserved 计入 held → 用户额度永久 -1，且原 recycle_due() 只动 accounts 表、不碰账本，无从自愈。代码里 CLAIM_STATES 已定义 uncertain 却从未使用。

修复：

RESERVED_TTL = 7200      # 2 小时

def settle_stale_reserved(ttl=RESERVED_TTL):
    # state IN ('reserved','uncertain') AND created <= now-ttl
    # → state='released', reason='预留超时自动归还'，逐条写 audit credit_release_stale

scheduler() 每分钟调用一次（marks["stale"] != (day, hm) 去重），容器重启后首轮即自愈。 2 小时阈值的安全边界：单次 claim 最长 180s，20 账号串行实测约 20s，远小于 TTL， 不会误伤正在进行的领取。

一个必须说清的点

以上是「到判定」的耗时（读 rawData 判断能不能领）。真实点击还要加 pg.click() 约 0.1s，award 响应返回约 0.2s。

参考站声明「全站最多 2 并发」，若夜间也按 2 并发跑，20 账号约 7 秒完成。

2026-10-18 夜间领取改成真并发（全部账号同时抢）

先发现：原来的「并发」是假的

pdd.py 只有一个 _BrowserWorker（单线程 + 一个 queue），所有 Playwright 调用排队执行。 在 server 层开线程池调 claim() 并不会加速，只是排队等同一个 worker —— 所以之前 Semaphore(2) 的「2 并发」也只是限流，不是并行。

改法（5 处）

  1. worker 池：_WORKER → _WORKERS 列表 + _worker_at(idx)，每个账号按需新建独立线程/浏览器；预热时分配固定 slot，00:00 claim 回到同一 slot 复用页面。
  2. run_nightly 三阶段： - 阶段 1 串行预筛 + 先插 reserved 占住额度（并发前串行算，避免超发） - 阶段 2 全部账号同时 check/claim，只跑网络不写库（避开 SQLite 写锁打架） - 阶段 3 串行结算：ledger / history / audit / 托管状态
  3. prepare_nightly 预热也并发（原来 20 账号串行 46s）。
  4. 夜间结束释放内存：pdd.pool_shutdown() 关浏览器线程 + _WARM.clear()，调度器在 run_nightly 后和 00:20 各调一次。
  5. 并发上限 PDD_NIGHTLY_PARALLEL，默认 6。

内存实测与坑

  • 每个浏览器实例约 460MB（预热页面后），2 账号 928MB，回收后降到 318MB。
  • 坑：容器内 /proc/meminfo 显示 MemTotal 64GB、available 18.8GB，但宿主机 free -m 只有 8GB（swap 2048MB 已用 1751MB）。容器读到的是外层宿主的视图，不能拿它算并发数，否则会误判成还能开 30 个浏览器，把 swap 打穿触发 OOM。
  • 因此改成固定上限 6（6 × 460MB ≈ 2.8GB），留 3GB 给宝塔上的 CPA / 青龙。
