# 云视听反代切回 Lucky 直连（2026-11-10）

## 背景

云视听解析服务出现域名打不开。现场检查发现后端服务本身在线，但公开 DNS 记录错误地指向内网地址，且 Lucky 的 HTTPS 父规则内没有该域名的反向代理子规则。

用户明确要求：云视听走 Lucky 反向代理，不经过 Cloudflare 代理。

## 结论

固定链路为：

```text
客户端
→ qqvideo.example.com:2333（灰云 DNS，仅解析）
→ 公网 Lucky:2333
→ HTTPS 内网后端:18081
```

Cloudflare 只承载权威 DNS，记录必须是 `proxied=false`；流量不经过 Cloudflare 边缘代理。

> 域名纠正：首次处理误用了另一域名。误加的 Lucky 子规则、单域名证书和 DNS 改动均已按变更前快照精确回滚；正确入口固定为 `qqvideo.example.com:2333`。

## 落地

1. 备份 Lucky 父规则、Lucky 配置文件和原 DNS 记录。
2. 在 Lucky 的 TLS 父规则 `2333` 中新增云视听子规则：
   - 域名：云视听专用域名
   - 上游：`https://<LAN-BACKEND>:18081`
   - 启用：是
   - 上游证书校验跳过：是（内网固定受控后端）
3. 将 `qqvideo.example.com` A 记录新增为 Lucky 的公网 DDNS 地址，保持灰云。
4. 复用 Lucky 中现有的 `*.example.com` Let's Encrypt 泛域名证书；无需另导入单域名证书。

## 验证方式

- 后端三个 systemd 服务均为 active，端口 `18081` 与 Chrome CDP 端口正常监听。
- Lucky API 回读：父规则启用、监听 2333、TLS 开启、云视听子规则恰好 1 条。
- Cloudflare DNS API 回读：云视听 A 记录指向 Lucky 公网入口，`proxied=false`。
- Cloudflare DoH 与 Google DoH 均返回 Lucky 公网地址。
- 严格 TLS（不使用 `-k`）分别通过内网 Lucky 和公网 Lucky：证书校验结果为 0，SAN 匹配云视听域名。
- 根路径返回后端应用的 404，而非 Lucky 404；专用管理路径返回后端应用级响应，证明 Host 路由和上游链路实际贯通。

## 实际结果

链路恢复：DNS → 公网 Lucky:2333 → 内网 HTTPS 后端:18081。公网与内网两条严格 TLS 测试均通过。

## 运维注意

- 云视听域名禁止切橙云。
- 客户端入口必须包含 `:2333`；直接访问默认 443 不属于本链路。
- 后端证书续期后，Lucky 中导入的文件证书不会自动跟随更新。续期时应同步更新 Lucky 证书，或后续改成安全的自动证书同步流程。
- Lucky 新增域名后必须检查实际 SNI 证书，不能只用 `curl -k` 验收；默认自签证书会制造“反代 200 但客户端打不开”的假成功。
