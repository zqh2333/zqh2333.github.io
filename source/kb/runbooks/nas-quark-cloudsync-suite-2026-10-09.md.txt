# NAS 夸克同步套件（bind + 原生 Cloud Sync）

## 目标
把 NAS `/volume1/云`（503 GB / ~33.8k 文件）同步到**夸克网盘**，用**原生 Cloud Sync**，
体验和「百度云」任务一致（DSM 界面可见、逐文件进度、断点续传）。

## 三个必须绕过的限制（实测）

| 现象 | 真因 | 绕过 |
|---|---|---|
| `418 Local syncfolder has been used` | 本地目录重叠，**前缀级**判断（父目录被占，子目录也不行） | `mount --bind` 换路径（418 按**路径字符串**判断，非 inode） |
| `417 account has been linked` | 一个 WebDAV 账号默认只能建一个任务 | 覆盖 `unique_id` 加后缀（如 `...#yun`） |
| 删任务报 `103`/`120` | 方法名/参数名错 | `unlink_connection` + **`connection_id=<id>`** |

## ★ 关键验证：bind 对同步真的有效（不是只有建任务有效）

曾一度怀疑「Cloud Sync worker 穿不透 bind」，实测**否定**：

- worker 与本机**同一 mount namespace**（`mnt:[4026531840]`），`/proc/<pid>/mountinfo` 里能看到 bind。
- 建任务后 `unfinished_files` 从 0 → **10010** 并持续下降。
- Cloud Sync 日志 `session_id=8` 大量 `err=0`，路径 `/docker/quark-sync/云/...`。
- 夸克端实际落盘：`/quark/云/DIY/BOM_PCB...csv`、`/quark/云/闲鱼/...apk` 等。

**★ 教训**：3.3 万文件首次**枚举要数分钟**才开始传。建任务后 1~2 分钟看"远端为空"
**不等于失败** —— 必须等枚举完再判断。


## ★★ 开机自恢复机制（bind 重启会丢，必须固化）

**关键事实：DSM 7 的 PID 1 是 `systemd`**（不是 sysvinit）。
`/etc/rc`、`/etc/rc.local` 都**不存在**；`rc.d` 也不是 DSM 原生机制。

Synology 的 `rc.d` 实际由 **`pkg-rclocal.service`** 驱动：

```sh
# /usr/syno/lib/systemd/scripts/pkg-rclocal.sh
for sh in $(/bin/ls -1 /usr/local/etc/rc.d/*.sh 2>/dev/null | sort); do
    $sh start || true          # ← 注意：带参数 start
done
```

它属于 `syno-bootup-done.target`（**很晚**），而 Cloud Sync 属于
`syno-low-priority-packages.target` → **rc.d 晚于 CloudSync 启动**。

**因此采用双保险：**

1. **主 = 自定义 systemd 单元 `quark-sync-bind.service`**（`systemctl enable`）
   - `After=pkg-volume.target syno-volume.target`（等 /volume1）
   - `Before=pkgctl-CloudSync.service`（**在 Cloud Sync 之前** bind）
   - → Cloud Sync 一启动就看到完整目录，**无需重启**，零打扰
2. **兜底 = `/usr/local/etc/rc.d/quark-sync-bind.sh start`**
   - 只在「发现 bind 缺失并补上」时才 `synopkg restart CloudSync` 重扫
   - 正常情况（主机制生效）识别到「已挂载」→ 0 秒返回，不打扰

**其它实测坑**：
- NAS 上**没有 `systemd-run`** → 不能用瞬态定时器做「延迟重启」。
- systemd oneshot 服务里 `cmd &` 起的后台进程会被 cgroup 杀掉 → 别用后台延迟。
- 用 `synopkg restart CloudSync` 会**同时重启百度云任务**（短暂中断）。

## 任务参数

| 项 | 值 |
|---|---|
| 任务名 / id | `云→夸克` / **id=13** |
| 本地 / 远程 | `/docker/quark-sync/云` → `/quark/云` |
| 方向 | `ONLY_UPLOAD`（只上传） |
| 保险丝 | `no_delete = true`（**永不删远端**） |
| unique_id | `127.0.0.1:5244:admin#yun` |
| 远程通道 | Alist WebDAV `http://127.0.0.1:5244/dav` |

## 日常操作

```sh
/volume1/docker/quark-sync/bin/verify.sh     # 健康检查（bind/inode/文件数/任务状态）
/volume1/docker/quark-sync/bin/bind.sh       # 手动恢复 bind
tail -20 /var/log/quark-sync-bind.log        # bind 日志
```

## 撤销

```sh
# 1. 删任务（connection_id=<id>）
# 2. umount /volume1/docker/quark-sync/云
# 3. rm /usr/local/etc/rc.d/quark-sync-bind.sh
```

## 限制与风险

- **夸克上传封顶 ~500 KB/s**（账号级限速，本机无解）→ 503 GB 首轮 **≥ 11.6 天**。
- **★逐文件延迟高（实测）**：Alist WebDAV 每项（含建目录）约 **60–90 秒**
  （日志时间戳：`IPTV.apk` → `图片/Pictures` 相隔 63s）。
  → 33,810 个文件的**文件数开销**可能比带宽更致命（`备份/` 有 26,002 个小文件）。
- **夸克 Cookie 约 13 天过期** → 靠 `alist_quark_cookie_sync.py` 定时保活，临界但够用。
- 开机单元/钩子若被 DSM 大版本更新清掉 → 重启后 bind 不恢复，同步**静默停**
  （因 `no_delete=true`，**不会误删**夸克上的文件）。
- Alist `:5244` 只绑 `127.0.0.1`（有意隔离），LAN 访问不到属正常。
