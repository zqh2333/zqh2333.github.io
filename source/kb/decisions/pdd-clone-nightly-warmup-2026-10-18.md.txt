## 改造前的问题

1. 调度 `while True: ... time.sleep(20)`，`hm == 0` 只在分钟窗口成立 →
   实际触发落在 **00:00:00–00:00:19** 之间，最坏晚 19 秒。
2. `claim()` 每次都新建 context + 打开活动页 + **`wait_for_timeout(2500)` 硬等 2.5 秒**。
3. 没有 23:57 准备环节；没有 23:55–00:20 手动核验避让。

单账号最坏要 00:00:24 才点到按钮，多账号串行更久。

## 改造内容

### pdd.py（5 处）

- 新增 `_WARM` 预热池 + `warm_prepare / warm_drop / warm_drop_all / warm_info`。
  预热**只建 context + 注入 Cookie，不发页面请求**，请求数不变。
- 新增 `_wait_state(pg, timeout_ms=9000)`：轮询 `window.rawData`，就绪即返回，
  替代固定 2.5 秒硬等。
- `claim(account, ck_info, warm=False)`：`warm=True` 时复用预热 context；
  结束时 `pg.close()` + `ctx.close()`，用完即回收。
- `MockProvider.claim` 同步签名。

### server.py（4 处）

- `scheduler()` 改为**按整分对齐**：`time.sleep(max(0.25, 60 - time.time() % 60))`，
  保证 `23:57:00` / `00:00:00` 准点命中（误差 < 50ms）。
- 新增 `prepare_nightly()`：23:57 只对 `hosting_state='active'` 且
  `snapshot.status == 'ready'` 的账号预热（不可领的账号预热了也没用）。
- `run_nightly` 调 `claim(..., warm=True)`；领取结束 `warm_drop_all()`；
  00:20 再清一次，防上下文泄漏。
- 新增 `rush_window()`：`23:55–00:20` 内 `/api/accounts/<id>/refresh` 返回
  429「抢券时段，手动核验已暂停」，避免手动核验抢占浏览器线程。

## 隐患修复：reserved 额度僵死自愈

**问题**：`run_nightly` 在 `claim()` 前插一条 `credit_ledger.state='reserved'` 占用 1 次额度。
成功转 `spent`、失败转 `released`，但**进程若在 claim 途中被杀，这条永远停在 `reserved`**。
`user_credits()` 把 `reserved` 计入 `held` → 用户额度永久 -1，且原 `recycle_due()` 只动
`accounts` 表、不碰账本，无从自愈。代码里 `CLAIM_STATES` 已定义 `uncertain` 却从未使用。

**修复**：

```python
RESERVED_TTL = 7200      # 2 小时

def settle_stale_reserved(ttl=RESERVED_TTL):
    # state IN ('reserved','uncertain') AND created <= now-ttl
    # → state='released', reason='预留超时自动归还'，逐条写 audit credit_release_stale
```

`scheduler()` 每分钟调用一次（`marks["stale"] != (day, hm)` 去重），容器重启后首轮即自愈。
2 小时阈值的安全边界：单次 claim 最长 180s，20 账号串行实测约 20s，远小于 TTL，
不会误伤正在进行的领取。

**沙盒验证（生产库副本，5 条断言全 PASS）**：

| 账本 | 结果 |
|---|---|
| reserved 3 小时前 | → released ✅ |
| uncertain 3 小时前 | → released ✅ |
| reserved 1 小时前 | 保留 ✅ |
| reserved 10 分钟前 | 保留 ✅ |
| spent 3 小时前 | 不动 ✅ |

`held` 从 4 降到 2，`audit` 写入 2 条 `credit_release_stale`。

**生产验证**：容器重启后 healthy，首次执行归还 0 条（无残留），`admin` 额度
`held=0`，首页 HTTP 200。

**未做**：参考站「后台每分钟最多检查 2 个活动托管记录、同号间隔 5 分钟」的上游巡检回收。
本方 `recycle_due()` 保持纯本地 deadline 判断（不发请求，无风控风险），结果一致。

## 2026-10-18 抢券提速：把「到判定」压进 1 秒

### 先分段计时找瓶颈（3 次，真实活动页）

| 阶段 | 均值 |
|---|---|
| `ctx.new_page()` | 0.051s |
| **`pg.goto(wait_until="domcontentloaded")`** | **0.945s（93%）** |
| `_wait_state()` 读 rawData | 0.024s |
| 合计 | **1.019s** |

瓶颈就是 `goto`：等整个 HTML 下载 + 解析完才返回。

### 三种取数方式实测对比

| 方式 | goto | wait | 合计均值 | 最小 |
|---|---|---|---|---|
| `domcontentloaded`（原始） | 1.15s | 0.02s | 1.076s | 0.850 |
| `commit`（拿响应头就走） | 0.15s | 0.63s | 0.784s | 0.641 |
| 预访问一次后再 goto | 0.61s | 0.02s | **0.644s** | 0.638 |

`commit` 只是把等待从 goto 挪到 `_wait_state`，总时长抖动大；**预访问后连接复用**才是真收益。

### 再比：保留页面 reload vs 新建 page

| 方式 | 合计均值 | 最小 |
|---|---|---|
| 预热保留 page，00:00 `pg.reload()` | **0.618s** | 0.589 |
| 预热只建连接，00:00 新建 page + goto | 0.785s | 0.755 |

reload 复用同一渲染进程，再省 0.167s。

### 最终改动（`/app/pdd.py`）

1. `warm_prepare()`：建 ctx 后**加载活动页并常驻**，存入 `_WARM[acc_id]["pg"]`（23:57 执行）
2. `claim(warm=True)`：复用常驻 page，用 `pg.reload(wait_until="domcontentloaded")` 取新数据，失败则回退 `goto`
3. `_wait_state()` 轮询 150ms → **40ms**
4. award 响应轮询固定 400ms → **30ms 起，命中即走**

### 实测（生产容器，真实网络）

| 场景 | claim 耗时 |
|---|---|
| 预热后立即领取（3 轮） | **0.637 / 0.645 / 0.657s** |
| 预热后间隔 **180 秒**（模拟 23:57→00:00） | **0.761s** |

对比基线 1.019s，**省 0.37s（36%）**。3 分钟间隔后连接部分失效但仍 <1s，
因为 reload 仍能复用 DNS 缓存与 TLS session。

### 一个必须说清的点

以上是「**到判定**」的耗时（读 rawData 判断能不能领）。真实点击还要加 `pg.click()`
约 0.1s，award 响应返回约 0.2s。

**但抢券胜负由「点击时刻」决定，不是响应返回时刻** —— 请求发出后服务端按到达顺序判库存。
所以关键指标是：00:00:00 → 点击 ≈ **0.75～0.87s**，仍在 1 秒内。

### 真正的瓶颈不在单账号，在串行

`run_nightly` 目前串行处理账号：0.65s/个，**20 个账号需要约 13 秒**，
第 20 个账号要到 00:00:13 才点击。这是抢券的真实短板。

参考站声明「全站最多 2 并发」，若夜间也按 2 并发跑，20 账号约 7 秒完成。
